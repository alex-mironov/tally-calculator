# Tally as a native SwiftUI app — migration plan

*19 Sep 2026. Status: plan only, nothing built.*

**Decision taken:** rewrite Tally as a pure Swift/SwiftUI app in a **new Xcode
project**, drop Expo and React Native entirely, **iOS only**, **universal
(iPhone + iPad)**. `web/` — the TanStack Start share site and its API — is out
of scope and does not change.

This is not a port of the React tree into SwiftUI view-by-view. Roughly a third
of `mobile/src` exists only to make SwiftUI reachable through a bridge, and
that third is deleted rather than translated. What is actually being rebuilt is
smaller than the line count suggests.

## What is there today

| Piece | Size | Fate |
|---|---|---|
| `src/lib/calc-engine.ts` | 158 | **Port carefully** — the one behavioural risk |
| `src/lib/tally-store.tsx` | 646 | Port: pipeline + persistence + prefs |
| `src/lib/storage.ts`, `share-link.ts`, `haptics.ts` | 183 | Port, straightforwardly |
| `src/app/index.tsx` | 1022 | Rebuild — ~40% is bridge workarounds |
| `saved` / `settings` / `tags` / `share/[id]` | 1006 | Rebuild as `List` / `Form` |
| `src/components/tally/*` | 1585 | Mostly **deleted**, see below |
| `src/constants/tokens.ts`, `tally-theme.ts` | 305 | Transcribe to Swift constants |
| `modules/tally-sheet/ios/*.swift` | 598 | **Keep the SwiftUI views**, drop the plumbing |
| `modules/icloud-kv/ios/*.swift` | 75 | Keep, minus the Expo module wrapper |
| `modules/list-scroll`, `modules/key-click` | 178 | **Delete** — both are bridge-only |

`mobile/ios/` is not committed; it's regenerated by `expo prebuild`. Nothing of
value is lost by starting a new project, and the new project becomes the
committed source of truth for the first time.

## What goes away

This is the case for the rewrite, so it's worth being specific. Every item
below exists *only* because SwiftUI is being reached through React Native:

- **`grouped-list.tsx` (313 lines), in full.** A row hosted from RN
  (`RNHostView`) isn't laid out inside the section's inset, so the file
  hand-compensates with `ROW_INSET`; `listRowInsets` no-ops when every value is
  `0`, so it passes `0.01`; `@expo/ui` has no `listRowSeparatorTint`, so every
  separator is redrawn in RN. SwiftUI has `.listRowInsets` and
  `.listRowSeparatorTint` and lays its own rows out. The file also carries an
  **entire second list renderer** (`GroupedCard`/`CardRow`) purely because a
  hosted SwiftUI `List` can't drive a large title's collapse — which is why
  Settings and Tags look like the other screens rather than being them.
- **`modules/list-scroll` (113 lines of Swift + TS).** Walks the view tree to
  find the `UICollectionView` behind a SwiftUI `List` so it can scroll it, and
  again to reach `topEdgeEffect`. In a project that owns the view builder these
  are `ScrollViewReader.scrollTo(_:)` and
  `.scrollEdgeEffectStyle(.hidden, for: .top)`.
- **`draft-line.tsx` (135 lines).** A `scaleX(-1)` mirrored scroll view with its
  content mirrored back, plus `MaskedView` + `expo-linear-gradient`, to keep a
  growing line anchored to its trailing edge under a fade. SwiftUI:
  `.defaultScrollAnchor(.trailing)` and `.mask { LinearGradient(...) }`.
- **The bar-button hit-testing workarounds.** `frame(44×44)` + `contentShape`
  applied to the *label* rather than the control, in four places, because a
  string-label `Button`/`Menu` hit-tests only its glyph across the bridge. Also
  why the title's pull-down menu was abandoned (a `ReactNode` label renders
  nothing in a nav-bar title view).
- **The Fabric responder workaround** in the entry card: the tap target is an
  `absoluteFill` *sibling* under the content with `box-none` on the row,
  because a scroll view under a `Pressable` ancestor never scrolls on the new
  architecture.
- **The `noteLive` ref**, guarding against the late `onChangeText` iOS delivers
  to a field that is being torn down.
- **The React Compiler minefield.** One `eslint-disable`, one `.value =` after
  a hook, or one `try/finally` silently un-memoises a whole component — a
  standing constraint on how every file in `src/` may be written, for a
  performance property a native app has by construction.
- **Native-sheet theming.** The app's theme is JS-only, so presented view
  controllers need `overrideUserInterfaceStyle` plus an opaque SwiftUI backdrop.
  Natively the theme *is* the environment.
- **`ScreenBackground`.** Two `LinearGradient`s approximating radial blooms
  because RN has no radial gradient. `RadialGradient` is what the design asked
  for in the first place.
- **Dead weight in the bundle:** `@shopify/react-native-skia`, `expo-device`,
  `expo-image`, `expo-linking`, `expo-web-browser`, `react-dom`,
  `react-native-web` are all dependencies that nothing imports.

Also gone: Expo SDK upgrades, `@expo/ui` version churn, `pod install` needing
rvm ruby 3.3.7 and a UTF-8 locale, and the `expo prebuild` round-trip in the
release lane.

## What must not change

These are hard constraints on the rewrite, not preferences:

1. **Bundle id `app.tally-calculator`, URL scheme `tally://`, the iCloud
   container and the `match` repo.** Same app record, same TestFlight/App Store
   lineage, same shared team distribution cert — never regenerate it (see
   `DISTRIBUTION.md`).
2. **The four persisted keys** — `tally:entries`, `tally:config`, `tally:tabs`,
   `tally:tagcatalog` — and their exact JSON. iCloud KV is a *shared* store: a
   user mid-rollout may have the old build on one device and the new one on
   another, and both must read what the other wrote.
3. **The `Entry` wire shape**, because `web/src/lib/share.ts` decodes it and
   `POST /api/shares` is frozen. Note that `excluded` and `error` are **absent**
   when false and `num` may be missing on old data — Swift's synthesised
   `Codable` will emit `"excluded": false` unless the fields are `Bool?` encoded
   with `encodeIfPresent`.
4. **`calc-engine` semantics**, because `web/src/lib/format.ts` mirrors it. A
   share link rendered on the web must produce the same numbers as the app that
   created it.

## The genuinely risky part

`calc-engine.ts` is 158 lines and it decides what people's money adds up to. The
subtleties that a careless port will get wrong:

- unary minus tracked as a `neg` flag through a token stream, including
  `−−5`;
- iOS-style percent, where `%` after `+`/`-` is relative to the previous value
  (`200+10%` = 220) but otherwise is `/100`;
- the two-pass precedence walk (`×÷` folded first, then `+−` left to right);
- a trailing operator dropped as an incomplete expression;
- an unresolvable reference poisoning the *whole* expression to `null` rather
  than resolving to 0;
- `fmt` hand-rolled on purpose, because Hermes' `Intl` varies by platform — the
  Swift version must not "improve" this into a `NumberFormatter`.

**Mitigation, and the first thing to build:** generate a corpus of a few
thousand expressions (including reference tokens), run the *TypeScript* engine
over it, and commit the `(input, refs, expected)` table as a fixture. The Swift
engine's test suite is that table. Same fixture can later be run against
`web/src/lib/format.ts` to keep all three honest.

## iPad — this is new work

The app has never run on iPad. `app.json` pins `orientation: portrait`, and
nothing in the layout handles landscape or a regular width class. The keypad
stow gesture in particular assumes a tall, narrow screen where the pad is ~40%
of the height; a full-width 4×5 keypad on a 13" iPad is absurd.

Decide early (it shapes Phase 3):

- **Cheap:** one column, capped at ~440pt and centred, phone layout intact at
  every size. A day's work, looks like a blown-up phone app.
- **Right:** in regular width, the list takes the leading side and the entry
  card + keypad a trailing pane of fixed width; Saved becomes a
  `NavigationSplitView` sidebar. A real design exercise, and the thing that
  makes an iPad build worth shipping.

Either way iPad brings: form-sheet presentation for the save/select sheets
(they currently assume compact width and drag detents), pointer hover states on
the keys, Stage Manager's arbitrary widths rather than three size classes, and —
nearly free, and a genuine feature — hardware keyboard entry via `.onKeyPress`.

## Phases

Each phase ends somewhere you can run and look at.

**Phase 0 — fences.** New project at `app/` (top level, committed; `mobile/`
stays intact and runnable until cutover). Bundle id, entitlements, scheme,
`match` profile wired. Pick the deployment floor: **iOS 26** deletes every
`isLiquidGlassAvailable()` fallback path and lets the design be one thing
instead of two — recommended unless the install base says otherwise. Pick the
iPad layout from the two above. *½ day.*

**Phase 1 — `TallyKit`, tests first.** A Swift package with no UI:
`Expression.swift` (the engine, against the generated fixture), the `Entry`/
`Tab` `Codable` types with hand-written encoding, `Pipeline.swift`
(`assignNums` → `freezeRefs` → `recalc`), `TallyStore` as an `@Observable`
class with the same surface the React context has today, and `Storage.swift`
(local cache + `NSUbiquitousKeyValueStore`, read-prefers-cloud, write-through,
`didChangeExternally` listener). Nothing here is guesswork; it's a transcription
with a test suite. *3–4 days.*

**Phase 2 — shell and design system.** SwiftUI `App`, `NavigationStack`,
`onOpenURL` for `tally://share/<id>`. Geist bundled; `Font` extension mirroring
`TallyFonts`. `tokens.ts` + `tally-theme.ts` transcribed to a `Theme` struct
keeping the exact same names (`ink2`, `accentInk`, `rowSel`, …) so the design
doc still reads true — and keeping the 4pt-grid rule. `ScreenBackground` as a
real `RadialGradient`. The `Haptic` vocabulary. *2 days.*

**Phase 3 — the calculator.** Native `List` with real `swipeActions` and
`contextMenu`; the keypad as a grid with `.glassEffect()`; the entry card;
`DraftLine`; the total bar; the stow gesture and keyboard avoidance (keep the
"whichever wants it shut further wins" rule — and `.ignoresSafeArea(.keyboard)`
on the root, because SwiftUI's automatic avoidance will otherwise fight the
hand-driven height). Select mode keeps its **own** checkmark rows rather than
`List(selection:)` — edit mode's grey highlight escapes an inset-grouped card.
Parity against the current build, screen by screen. *~1 week.*

**Phase 4 — the rest.** Saved (`List` + `.searchable` + the glass filter
strip), Settings and Tags as `Form`s that finally get their large titles
honestly, the save and selection sheets — `modules/tally-sheet`'s SwiftUI views
lift across almost unchanged once the `Record`/`Module`/promise plumbing comes
off — and the share-import screen. *~1 week.*

**Phase 5 — iPad and adaptivity.** The layout chosen in Phase 0, landscape,
form sheets, pointer states, hardware keyboard. *3–5 days.*

**Phase 6 — migration and cutover.** *Done, 20 Sep.*

The **AsyncStorage importer was dropped**, not built: the app has never shipped
to production, so there is no installed base whose local-only data needed
carrying across. That was the single riskiest item in this plan and it turned
out not to exist. (The *other* compatibility constraints still hold, and are
still tested — `web/src/lib/share.ts` decodes `Entry` and `web/src/lib/format.ts`
mirrors the engine, and the share API is deployed.)

What was done: fastlane moved to `app/` with `expo prebuild` replaced by
XcodeGen and CocoaPods dropped entirely; secrets backed up out of the repo
before anything was removed; an iOS CI workflow to match the web one, left
manual-only until it has had a green run; `mobile/` deleted.

**Total: roughly 4–5 weeks of focused work.** The two phases that will overrun
are 3 (the stow/keyboard choreography is fiddly in any framework) and 5 (if the
"right" iPad layout is chosen, which it should be).

## What you give up

- **Android, permanently.** Accepted — there is no `android/` directory, the
  release lane is iOS-only, and the design leans on Liquid Glass and SF Symbols.
- **Nothing else, really.** There is no `expo-updates` in the dependency tree,
  so no OTA update capability is being lost; every change already needs a build.

## Decisions taken

*19 Sep 2026.*

- **Deployment floor: iOS 26.** Liquid Glass is unconditional. Every
  `isLiquidGlassAvailable()` branch, both fallback renderers and the opaque
  twin of the design are deleted rather than rewritten in Swift; `.glassEffect`,
  `.scrollEdgeEffectStyle` and the newer `List` modifiers are used without
  availability checks.
- **Phases 1–4 are done** (engine + pipeline + store; app target + design
  system; the calculator screen; Saved, Settings, Tags, the save sheet and
  sharing). Phase 3 found that two of the workarounds listed below are not just
  unnecessary but *wrong* in a native app — see `app/README.md`. Phase 5 (iPad)
  and Phase 6 (migration and cutover) remain.
- **iPad: split layout in regular width.** List on the leading side, entry card
  + keypad in a fixed-width trailing pane; Saved becomes a
  `NavigationSplitView` sidebar. Compact width keeps the phone layout.

  *Done, 20 Sep — but not with `NavigationSplitView`.* Four ways of deciding
  the layout from inside the calculator all failed while it was a split view's
  detail column, because a detail column's width is re-proposed as the sidebar
  moves and the width reaching the branch disagreed with the width reaching the
  container. The arrangement is a plain `HStack` in `RootView` instead: it
  measures the window, subtracts a fixed sidebar, and passes the answer down as
  a parameter, so the calculator does no geometry at all. Cost: the system
  sidebar toggle, redrawn in the toolbar. See the note on `wideLayout`.

## Open questions

- Does the rewrite keep Geist, or is this the moment to take the design's
  original SF / Spline Sans Mono? Geist was a deliberate divergence; a native
  app makes Dynamic Type and the system faces much cheaper to honour.
- `TallyStore` as one `@Observable` (matching today's single context) or split
  into `TabStore` / `Preferences` / `TagCatalog`? The single object is a
  faithful port and the safer Phase 1; splitting is easy afterwards.
- Should the generated engine fixture live in this repo (shared by Swift, TS
  and the Worker) or be regenerated per test run? Committed is more reviewable.
- Is the share API worth a Swift client generated from the same types, or does
  a 40-line `URLSession` wrapper suffice? (It suffices.)
